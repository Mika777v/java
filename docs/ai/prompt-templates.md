# 依頼文テンプレート(AI 向け)

Claude / Copilot に頼むときにコピーして使う依頼文です。`<...>` を書き換えてください。
どのテンプレートも、最初に `docs/ai/` を読ませることで、毎回同じ前提を説明しなくて済むようにしています。

## 共通の前置き(どの依頼にも付ける)

```
CLAUDE.md の「AI 開発運用ルール」と、docs/ai/ の project-context.md・conventions.md に従って作業してください。
- master に直接変更しない。作業ブランチで変更し、完了したら PR まで作る(マージは私がする)
- パスワードや認証情報をコード・ログに書かない
- 修正はタスクの範囲だけ。関係ないリファクタリングはしない
- DB 変更・API 互換性・認証・データ削除・仕様変更だけは、先に原因と方針を説明して確認を取る
- DEVLOG.md と SESSION_SUMMARY.md を更新する
- 説明は日本語で、専門用語を使いすぎずに
(Claude Code は CLAUDE.md を自動で読むので、この前置きは Copilot など、ほかの AI に頼むときに付けます)
```

## 1. 新しい機能を追加する

```
(共通の前置き)
<機能の説明>を追加したいです。

- 誰が使うか: <管理者 / 新入社員>
- 画面・URL のイメージ: <例: /me/password でパスワードを変更>
- 完了条件: <例: 新入社員が自分のパスワードを変えて、新しいパスワードでログインできる>

まず設計(URL、変更するファイル、テーブル変更の有無、テスト方針)を短く提案してください。
OK を出したら実装し、mvn test とスモークテスト相当の確認をしてから PR を作ってください。
architecture.md / database.md / backlog.md の更新も忘れずに。
```

## 2. バグを直す

```
(共通の前置き)
次の不具合を直してください。

- 起きたこと: <画面の表示やエラーメッセージをそのまま貼る>
- 手順: <どの画面で何をしたか>
- 期待する動き: <本来どうなってほしいか>
- 環境: <Codespaces / GitHub Actions のリンク>

まず原因と修正方針を説明してください。修正するときは、
不具合を再現するテストを先に書いて失敗することを確かめてから直してください。
```

## 3. GitHub Actions の失敗を調べる

```
(共通の前置き)
GitHub Actions が失敗しました: <Actions の実行 URL>
ログ(失敗したステップの最後の 50 行くらい):
<貼り付け>

原因を、どのステップの何が悪いのか分かるように説明してください。
「関係ない失敗(master でも失敗している等)」か「この変更が原因」かも判断してください。
```

## 4. Codespaces で動かないとき

```
(共通の前置き)
Codespaces でアプリが動きません。
- ターミナルの表示: <貼り付け>
- `cd onboarding-progress-system && docker compose ps` の結果: <貼り付け>
- `docker compose logs --tail 50 app` の結果: <貼り付け>

原因と、私が Codespaces で実行するコマンドを手順で教えてください。
```

## 5. テーブルを変更する

```
(共通の前置き)
docs/ai/database.md を読んでください。
<テーブル>に<列 / 制約>を追加したいです。理由: <なぜ必要か>

既存のマイグレーションは書き換えず、新しい V<番号>__*.sql で追加してください。
既存データがある場合の扱い(初期値など)と、サンプルデータ・テストへの影響を先に説明してください。
```

## 6. テストを追加する

```
(共通の前置き)
<クラス名 / 機能>のテストを追加してください。
conventions.md の「テスト」の書き方に合わせ、サンプルデータと固定日付(2026-10-15)を前提にしてください。
本体コードは変更しないでください。足りないケース(正常系・入力エラー・404・権限)を一覧にしてから書いてください。
```

## 7. コードの説明をしてもらう(変更なし)

```
docs/ai/architecture.md を読んだうえで、<クラス名 / 画面 / URL>が
どう動いているかを、Java に慣れていない人向けに説明してください。
コードは変更しないでください。
```

## 8. 現状レポートを更新する

```
(共通の前置き)
リポジトリの現状を調べて docs/current-status.md と docs/ai/ を最新にしてください。
特に URL 一覧、テーブル定義、テストの件数、バックログ(完了したもの・新しく見つかった課題)。
コードは変更せず、ドキュメントだけの PR にしてください。
```

## 9. PR のレビューを頼む

```
<PR の URL> をレビューしてください。conventions.md に沿っているか、
権限のチェック漏れ(新入社員が他人のデータを触れないか)、テスト不足、
既存マイグレーションの書き換えがないかを重点的に見てください。
指摘は「必ず直す」と「任意」に分けてください。
```

## 10. Claude Code のスキルを使う

`.claude/skills/` のスキルは、Claude Code に `/スキル名` と打つか、依頼文に名前を書くと使われます。

```
/project-memory-manager
現状を調べて、ドキュメントのずれと次にやるべきことを 3 つ教えてください。
```

```
/spring-boot-architect
このブランチの変更を、レイヤー構造と Flyway の観点でレビューしてください(コードは変えない)。
```

```
/feature-builder
<機能の説明>を追加したいです。まず要件の整理とタスク分解を見せて、私の了承を待ってください。
```

```
/review-and-refactor
<クラス名や画面>を整理したいです。候補と理由を先に一覧で出してください。直すのは私が選んだものだけにしてください。
```

## Copilot(エディタ内の補完・チャット)で使うときのコツ

- チャットでは `#file:docs/ai/conventions.md` のように関係ファイルを添付すると、既存スタイルに沿った提案になりやすい
- 新しいテストを書くときは、似た既存テスト(例: `TaskPageControllerTest.java`)を開いた状態で補完させる
- 「今日の日付」には `LocalDate.now(clock)` を使うよう、補完結果を必ず確認する(`LocalDate.now()` を提案されやすい)
- POST のテストは `WebTestSupport.post` を使っているか確認する(CSRF がないと 403)

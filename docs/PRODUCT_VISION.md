## 1. ひと言で

**「新入社員のやること管理」を、チームの仕事全体を扱える Jira / Backlog 風のチケット管理に育てる。**
作り直さず、今動いているコード・DB・画面をそのまま土台にして、少しずつ広げる。
移行の間も、今のオンボーディング管理は今までどおり使える。

---

## 2. なぜチケット管理へ進化させるのか

### 2.1 今のシステムで分かったこと

オンボーディング管理として必要な機能は、ほぼそろいました(2026-10-20 時点、PR #38 まで)。

| 今あるもの | チケット管理に置き換えると |
|---|---|
| タスク(全員共通のひな形)と割り当て(人ごとの実体) | チケットのテンプレートと、チケットそのもの |
| 割り当ての状態(未着手 / 対応中 / 完了)・期限・完了日時 | チケットのステータス・期限・完了日時 |
| サブ項目(チェックボックス) | チケットのチェックリスト |
| ダッシュボード、期限切れ、絞り込み | チケットのダッシュボード・検索 |
| 管理者 / 新入社員の役割、専用URL、パスワード | ユーザー管理・ログイン・権限 |
| CI(自動テスト 221 件 + Docker での確認)、Codespaces、ドキュメント一式 | そのまま使える開発基盤 |

つまり「**人に作業を割り当て、状態と期限で追いかける**」という仕組みの中心は、すでにできています。
足りないのは、オンボーディング以外の仕事を載せるための **一般化**(プロジェクト、担当者の変更、コメント、検索など)です。

### 2.2 進化させる理由

1. **同じ仕組みをオンボーディング以外にも使いたい**: 入社手続き以外の社内の依頼・作業管理・小さな開発案件も同じ形で管理できる
2. **ツールを分けたくない**: 受け入れ担当は、新入社員のフォローとふだんの業務を別のツールで見ている。1 か所で見られると楽になる
3. **既存資産の再利用で、少ない工数で作れる**: ゼロから作るより、動いているものを広げるほうが早く、壊れにくい(テストと CI がすでにある)
4. **学習テーマとしても良い**: Java / Spring Boot の学習を、実用的な「段階的な移行」「Feature Toggle」「DB の段階的変更」まで広げられる

## 3. 想定ユーザー

| ロール | 誰か | 主にやること |
|---|---|---|
| ADMIN(管理者) | システムの管理者(今の管理者) | ユーザー・プロジェクト・機能の ON/OFF の管理。すべての操作 |
| MANAGER(マネージャー) | チームリーダー、受け入れ担当 | プロジェクトの運営、チケットの起票・割り振り、進捗の確認 |
| MEMBER(メンバー) | チームメンバー、新入社員 | 自分に割り当てられたチケットを進める、コメントする、起票する |
| VIEWER(閲覧者) | 関係部署、上長 | 見るだけ(進み具合の確認) |

規模の想定: 1 つの会社・部署の中で、ユーザー数十〜100 人程度、プロジェクト数件〜数十件。
社内向け(インターネットに広く公開しない)という前提は、今と同じです。

> 注意: 今の `MEMBER` は「新入社員(専用URLでログイン)」の意味です。チケット管理では「一般のメンバー」の意味に広がるので、
> 役割とログイン方法を分けて考える必要があります(PRD の 2.3、ロードマップの Phase7)。

## 4. 解決したい課題

| 課題 | 今 | チケット管理で |
|---|---|---|
| オンボーディング以外の仕事を管理できない | タスクは全員共通のひな形しか作れない | 1 件ずつ自由に起票できるチケット |
| 仕事の置き場所が分けられない | 1 つのリストしかない | プロジェクトごとに分けられる |
| 状態が粗い | 未着手 / 対応中 / 完了 の 3 つ | TODO / IN_PROGRESS / REVIEW / DONE / CLOSED |
| やり取りが残らない | コメント欄がない(チャットなど外でやり取り) | チケットにコメントが残る |
| 探せない | 部署と進み具合での絞り込みだけ | 担当者・ステータス・キーワード・プロジェクトで検索 |
| 気づけない | ダッシュボードを見に行くしかない | 割り当て・コメント・期限の通知 |
| 権限が 2 種類しかない | 管理者 / 新入社員 | ADMIN / MANAGER / MEMBER / VIEWER |
| 全体の流れが見えにくい | 表だけ | カンバンボード |

## 5. MVP(最初に「チケット管理として使える」状態)

**Phase1〜Phase3 の完了時点** を MVP とします(目安: 開始から約 10 週)。

| MVP に含める | 含めない(後のフェーズ) |
|---|---|
| チケットの登録・編集・削除(タイトル、説明、担当者、期限、ステータス) | コメント(Phase4) |
| プロジェクトの作成と、チケットのプロジェクトへの所属(Project └ Ticket) | 高度な検索(Phase5。MVP は一覧の簡単な絞り込みのみ) |
| ステータス TODO / IN_PROGRESS / REVIEW / DONE / CLOSED | 通知(Phase6) |
| チケット番号(例: `ONB-12`) | 4 ロールの権限(Phase7。MVP は今の ADMIN / MEMBER のまま) |
| オンボーディングのタスクひな形から、チケットをまとめて起票 | ダッシュボードの作り直し(Phase8)、カンバン(Phase9) |
| すべて Feature Toggle `ticket-system` / `project-management` の配下 | |

MVP の間も、今のオンボーディング画面(タスク・割り当て・マイページ)は **そのまま使えます**。

## 6. 将来像(6 か月後)

```
            ┌─────────────── チケット管理プラットフォーム ───────────────┐
            │  プロジェクト A    プロジェクト B    オンボーディング(テンプレート) │
            │   └ チケット        └ チケット         └ 新入社員ごとにまとめて起票  │
            │       ├ コメント                                              │
            │       ├ チェックリスト(今のサブ項目)                           │
            │       └ 通知                                                  │
            │  検索 / ダッシュボード / カンバン / 4 ロールの権限              │
            └──────────────────────────────────────────────────────────┘
```

- オンボーディングは「プロジェクトの 1 つ + チケットのテンプレート」という位置づけになる
- 今のオンボーディング画面は、チケット側で同じことができるようになった時点で退役させる(Feature Toggle で切り替え、確認後に削除)
- それ以降の候補(6 か月より先): 添付ファイル、チケット同士の関連、時間の記録、メール通知、外部連携(Slack など)、REST API の拡充

## 7. やらないこと(このビジョンの範囲外)

| やらないこと | 理由 |
|---|---|
| 作り直し・全面リプレース・DB の全削除 | 動いているものを壊さない。段階的に育てる方針 |
| 複数の会社で共有する(マルチテナント) | 社内向けの前提。必要になったら別に検討 |
| Jira と同じ機能をすべて作る | 小さなチームで使う範囲に絞る(スプリント、バーンダウン、ワークフローの自由設定などは対象外) |
| JavaScript の画面フレームワークへの全面移行 | 今の Thymeleaf を活かす。カンバンのドラッグ操作だけ少し JavaScript を使う可能性がある(事前にオーナーに相談) |

## 8. 成功の目安

| 目安 | いつ |
|---|---|
| オンボーディングの利用が、移行中も止まらない(障害・使えない期間がゼロ) | 全期間 |
| オンボーディング以外の仕事を、チケットで 1 プロジェクト以上管理している | MVP(約 10 週) |
| 新入社員の受け入れを、チケット側(テンプレートからの起票)だけで回せる | Phase9 完了時(約 24 週) |
| 不要になった Feature Toggle と、旧オンボーディング画面の削除が終わる | 6 か月 |
| 自動テストと CI が、各 PR で緑のまま | 全期間 |

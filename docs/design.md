## 1. システム構成

```
 ブラウザ(管理者・新入社員)
      │  HTTPS(Codespaces などのプロキシ経由)
      ▼
 ┌──────────────── app コンテナ ────────────────┐
 │ Spring Boot(Java 21)                         │
 │  ├ Spring Security … ログイン・権限            │
 │  ├ Controller      … 画面・API の入口          │
 │  ├ Service         … 業務ルール                │
 │  ├ Repository(JPA)… DB の読み書き            │
 │  └ Thymeleaf       … 画面(HTML)を組み立てる  │
 └──────────────────────────────────────────────┘
      │ JDBC
      ▼
 ┌──── db コンテナ ────┐
 │ PostgreSQL 15        │  … テーブルと初期データは Flyway が自動で作る
 └──────────────────────┘
```

| 項目 | 選んだもの | 理由 |
|---|---|---|
| 言語・フレームワーク | Java 21 + Spring Boot 3.3 | Java の学習を兼ねるため。業務システムでよく使われる標準的な構成 |
| 画面 | Thymeleaf(サーバーで HTML を作る) | 小規模で、画面の動きは少なくてよい。JavaScript をほぼ書かずに済む |
| DB | PostgreSQL 15 | 一般的で、Docker で簡単に動かせる |
| DB の変更管理 | Flyway | テーブルの作り方を SQL ファイルで管理し、起動時に自動で反映できる |
| 実行 | Docker Compose | 1 コマンドで DB とアプリを起動できる。Codespaces でも同じ方法で動く |

## 2. 画面設計

### 2.1 画面一覧

| 画面 | URL | 使う人 |
|---|---|---|
| ログイン | `/login` | 管理者(パスワード方式の新入社員も) |
| 専用URL | `/join/{鍵}` | 新入社員(開くとマイページへ) |
| ダッシュボード | `/` | 管理者 |
| タスク一覧・登録・編集 | `/tasks`, `/tasks/new`, `/tasks/{id}/edit` | 管理者 |
| ユーザー一覧・登録・編集 | `/users`, `/users/new`, `/users/{id}/edit` | 管理者 |
| ユーザー詳細(割り当て・専用URL・パスワードのリセット) | `/users/{id}` | 管理者 |
| マイページ | `/me` | 新入社員 |
| パスワード変更 | `/me/password` | パスワードでログインする人 |
| エラー画面 | (404・403・その他) | 全員 |

### 2.2 画面の流れ

```
                ┌──────────── ログイン ────────────┐
                │                                    │
        (管理者)│                                    │(新入社員:専用URLを開く)
                ▼                                    ▼
          ダッシュボード ─→ ユーザー一覧 ─→ ユーザー詳細      マイページ
                │              │               │             (状態を変更)
                └→ タスク一覧   └→ 登録・編集    ├→ 割り当て
                     └→ 登録・編集              ├→ 専用URLの発行
                                               └→ パスワードのリセット

  ※ パスワードの変更が必要な人は、どの画面を開いても「パスワード変更」画面へ
```

### 2.3 画面の作りの決まりごと

- ボタンで登録・更新したら、別の画面へ移動させてから結果を表示する(**PRG パターン**。再読み込みで二重登録しないため)
- 結果のメッセージは緑の枠、エラーは赤の枠で、移動先の画面の上に 1 回だけ表示する
- 専用URLや仮パスワードは、発行した直後の画面に 1 回だけ表示する(黄色の枠)
- 画面移動の行き先は「パスだけ」(`/users/3` など)で返す。プロキシの裏でもアドレスがずれないため

## 3. データ設計

### 3.1 テーブルの関係

```
 users(ユーザー)  1 ──── * task_assignments(割り当て) * ──── 1 tasks(タスク)
   ├ 役割(管理者 / 新入社員)        ├ 状態(未着手 / 対応中 / 完了)    ├ タイトル・説明
   ├ パスワード(ハッシュ)           ├ 期限                            ├ 有効 / 無効
   ├ 専用URLの鍵(ハッシュ)・期限    └ 完了日時                        └ 表示順
   └ パスワード変更が必要か
```

- 同じ人に同じタスクは 1 回だけ(`user_id` と `task_id` の組み合わせを一意にする)
- ユーザーやタスクを消すと、その割り当ても DB が自動で消す
- 状態や役割は、DB に `'IN_PROGRESS'` のような文字で保存する(番号で保存すると、あとで順番を変えたときに意味が変わってしまうため)
- 日時は世界共通の時刻で保存し、画面では日本時間で表示する

### 3.2 初期データ

初回起動時に、サンプルのタスク 6 件(うち 1 件は無効、1 件はリンクの確認用)、ユーザー 3 人、割り当て 10 件が入ります。
詳しくは [現状レポート](current-status.md) の 4 章。

## 4. 権限設計

| 対象 | 管理者 | 新入社員 | ログインしていない人 |
|---|---|---|---|
| ログイン画面、専用URL、ヘルスチェック | ○ | ○ | ○ |
| マイページ、パスワード変更 | ○ | ○(自分のものだけ) | → ログイン画面へ |
| ダッシュボード、タスク、ユーザー、割り当て | ○ | ×(403) | → ログイン画面へ |
| REST API(`/api/...`) | ○(パスワードで認証) | ×(401 または 403) | ×(401) |

- 新しく画面を作ったときは、何も設定しなければ **管理者専用** になる(うっかり新入社員に見せないため)
- 新入社員の操作は、必ず「ログインしている本人のデータか」を確認する。他人のデータを指定されたら「見つからない」(404)にする

## 5. 主な処理の設計

### 5.1 専用URL(新入社員のログイン)

```
管理者が「発行」                                新入社員が URL を開く
  │                                              │
  ├ 推測できない乱数(32 バイト)を作る           ├ URL の鍵をハッシュにする
  ├ そのハッシュ(SHA-256)と有効期限を DB へ     ├ DB のハッシュと一致し、期限内か確認
  └ URL を画面に 1 回だけ表示                    ├ OK → ログイン状態にして /me へ移動
                                                 └ NG → 「このリンクは使えません」
```

- DB には鍵そのものを保存しないので、DB の中身が漏れても URL は分からない(その代わり、あとから表示できない)
- 再発行すると DB のハッシュが変わるので、古い URL は使えなくなる
- 開いたらすぐ `/me` へ移動するので、アドレス欄に鍵が残らない

**この方式にした理由:** 利用期間が短く公開もしないので、新入社員にパスワードを覚えてもらう手間のほうが大きいため(オーナーと相談して決定)。
パスワード方式も設定ひとつで戻せるように残しています(`APP_MEMBER_LOGIN=password`)。

### 5.2 パスワード

| 場面 | 処理 |
|---|---|
| 保存 | BCrypt でハッシュにして保存。元のパスワードは保存しない |
| 管理者がほかの人に設定・リセット | 「変更が必要」の印を付ける。本人はログイン後、パスワード変更画面以外を開けない |
| 本人が変更 | 現在のパスワードを確認してから変更し、印を外す |
| 管理者が 1 人だけで忘れた | 起動時の設定(`APP_ADMIN_PASSWORD_RESET=true`)で `.env` のパスワードに戻す。変更必須。使ったら設定を外す |

### 5.3 期限切れと進捗の計算

- 期限切れ = 期限が「今日」より前で、状態が完了ではないもの
- 「今日」は、アプリが持つ時計(日本時間)から取る。テストではこの時計を 2026-10-15 で止めて、いつ実行しても同じ結果になるようにしている
- 完了率 = 完了数 × 100 ÷ 割り当て数(小数点以下は切り捨て。割り当てがなければ 0%)
- ユーザーごとの集計は、DB で 1 回の問い合わせにまとめて計算する(人数が増えても遅くならないように)

### 5.4 説明欄のリンク

- `http://` / `https://` で始まる部分だけをリンクにし、ほかの文字は HTML として動かないように変換してから表示する
- リンクは新しいタブで開き、開いた先のサイトからこのアプリを操作されないようにする

## 6. 設定

| 設定(環境変数) | 内容 | 初期値 |
|---|---|---|
| `POSTGRES_PASSWORD` | DB のパスワード | なし(必須) |
| `APP_ADMIN_EMAIL` / `APP_ADMIN_PASSWORD` | 最初の管理者 | `admin@example.com` / なし(必須) |
| `APP_ADMIN_PASSWORD_RESET` | 最初の管理者のパスワードを戻す | `false` |
| `APP_MEMBER_LOGIN` | 新入社員のログイン方法(`link` / `password`) | `link` |
| `APP_ACCESS_LINK_VALID_DAYS` | 専用URLの有効日数 | `60` |
| `APP_BASE_URL` | 専用URLに表示するアドレス | 空(Codespaces では自動設定) |
| `APP_TIME_ZONE` | 「今日」の判断と表示のタイムゾーン | `Asia/Tokyo` |

Codespaces では、パスワードは初回起動時に自動で作られ、`onboarding-progress-system/.env`(Git には入らない)に保存されます。

## 7. テストと品質の設計

| 種類 | 内容 | どこで動くか |
|---|---|---|
| 自動テスト(184 件) | 画面・API・権限・業務ルールを、本物と同じ PostgreSQL(Testcontainers)で確認 | GitHub Actions の `test` |
| スモークテスト | Docker で実際に起動し、ログイン・専用URL・パスワード変更などを curl で一通り操作 | GitHub Actions の `run-smoke` |
| Codespaces での確認 | 人が画面を操作してチェックリスト 12 項目を確認 | [codespaces-check.md](codespaces-check.md) |

- 2 つの自動チェックが通らないと `master` にマージできない(ドキュメントだけの変更では省略)
- テストは「今日」を固定し、サンプルデータの件数などは 1 か所(`SampleData`)にまとめている
- 新しい機能では「わざとコードを壊すとテストが失敗するか」も確認している

## 8. 主な設計判断の記録

あとから「なぜこうなっているの?」と思ったときのための記録です。

| 決めたこと | 理由 | PR |
|---|---|---|
| 新入社員は専用URLでログイン(パスワードは切り替えで残す) | 短期間・非公開の利用なので、パスワード管理の手間を減らす | #19 |
| 専用URLはハッシュだけを保存し、1 回だけ表示 | DB が漏れても URL が分からないようにする | #19 |
| 管理者が設定したパスワードは初回に変更必須 | 管理者が知っているパスワードを使い続けないため | #20 |
| 画面移動の行き先はパスだけ | Codespaces などのプロキシの裏で、localhost に飛ばないため | #24 |
| ドキュメントだけの PR はテストを省略(スキップ扱い) | 必須チェックを満たしつつ、待ち時間をなくす | #26 |
| 専用URLの即時無効化はしない | 公開しない前提で影響が小さい | (見送り) |
| ユーザー・割り当ての REST API は作らない | 連携先がまだない | (保留) |
